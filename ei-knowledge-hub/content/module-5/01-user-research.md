# 用户调研 Playbook：开发者与实验室用户画像

在 SDK 产品立项前，必须先回答「为谁而建」。本章节聚焦两类核心用户：高校机器人实验室研究员，以及独立极客/初创团队开发者。调研目标不是收集愿望清单，而是验证假设、量化痛点优先级。

## PM视角要点

- 实验室用户关注「可复现的实验环境」和「论文/课题交付周期」；极客开发者关注「上手速度」和「社区案例」。同一 SDK，两类用户的成功标准不同。
- 访谈提纲应覆盖：当前技术栈（ROS 2 / 自研框架）、典型开发任务、最近一次接入失败的原因、愿意为哪些能力付费。
- 用户画像（Persona）不是虚构故事，而是访谈发现的聚类结果。每个画像需绑定 1 至 2 条可验证的核心痛点。
- PM 要区分「 stated need」（用户说的）和「observed behavior」（用户做的）。例如用户说想要完整文档，实际行为是只看 Quick Start 就跑示例。
- 输出物：2 份用户画像卡片 + 需求优先级列表（P0/P1/P2），为后续功能矩阵和 PRD 用户故事提供输入。

## 核心概念

| 概念 | 说明 |
|------|------|
| 高校实验室 Persona | 课题组负责人或研究生，需在学期内完成算法验证与论文实验，预算敏感、重视开源与可引用 |
| 极客开发者 Persona | 独立开发者或小团队工程师，追求快速 Demo、Hackathon 展示、二次创业可能性 |
| Jobs to be Done | 用户「雇佣」产品完成的任务，如「在一周内让机器狗完成避障巡线」 |
| 访谈假设 | 调研前写明的可证伪命题，例如「文档缺失是接入失败的首要原因」 |
| 痛点优先级矩阵 | 按频率 × 严重程度二维排序，避免被个别用户的强烈情绪带偏 |

### 实验室用户典型特征

- 使用 ROS 2、Gazebo/Isaac Sim 等仿真环境
- 需要多机协同、传感器数据录制与回放
- 采购决策受导师/设备处流程影响，周期长

### 极客开发者典型特征

- 偏好 Python SDK、Jupyter Notebook 示例
- 活跃在 GitHub、Discord、机器人社群
- 对价格敏感，但愿意为节省时间的工具付费

## 今日推荐资料

- [The Mom Test](https://www.momtestbook.com/)：用户访谈经典方法论，避免问出无效答案
- [Jobs to be Done 框架介绍](https://jtbd.info/)：从任务视角理解用户需求
- [ROS 2 社区与 Discourse](https://discourse.ros.org/)：观察真实开发者讨论与痛点
- [宇树开发者社区](https://www.unitree.com/)：国内四足机器人开发者生态参考
